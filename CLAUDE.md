# Vesper App

Internal sales and operations app for Vesper Lighting, Inc. (Calgary). Read this file and `docs/` before doing anything. The docs are the source of truth. If a request conflicts with them, say so and ask.

## What this app is

Vesper installs permanent exterior roofline lighting (24V RGBW nodes in an aluminum track under the soffit, app controlled, 10-year warranty). Sales are door to door. Appointment setters knock doors in the late afternoon and book evening meetings for the owner (Keenan), who meets the homeowner at dusk, presents on an iPad, prices the job, and closes. Installs are done by small crews. The app is the system of record for leads, meetings, quotes, and (later) jobs, crews and timesheets.

## Focus (Keenan, 2026-11-02)

The app's fundamentals are three things: the setter sessions (knocking, leads and booking), the sales meetings (meeting mode on the iPad), and the shareable quote links for customers. The current work is the shareable quote link. Everything else is parked until Keenan says otherwise: the pipeline board (M4), the sales dashboard (M6), the website lead form and daily email (M7), and the backlog ideas. Don't start or plan parked work, and don't suggest it.

V1 is the sales side only. See `docs/01-product-spec.md` for scope, `docs/02-data-model.md` for the schema, `docs/03-roadmap.md` for milestones and acceptance criteria, `docs/04-session-prompts.md` for how each build session is run, and `docs/05-supabase-setup.md` for the Supabase settings that live outside the code and how to set up a second project.

## Stack

- Next.js (App Router, TypeScript), Tailwind CSS, shadcn/ui components
- Supabase: Postgres, Auth, Storage (photos), Row Level Security on every table
- Vercel hosting, installable PWA (manifest, icons, service worker for caching only, no offline writes in V1). Functions run in `pdx1` (Portland), next to the Supabase database in us-west-2, set by `regions` in `vercel.json`
- Google Places Autocomplete for addresses (lat/lng saved on every lead)
- `@react-pdf/renderer` for quote PDFs
- Zod for validation, Vitest for unit tests (pricing and scheduling logic), Playwright for a smoke test of the main flows
- Server Actions for writes, Supabase client for reads. No separate API layer unless a route is public (the website lead form).

## Roles and who sees what

Three roles in `profiles.role`: `owner`, `sales`, `crew`. V1 uses `owner` and `sales`. `crew` exists in the schema but has no screens yet. In the UI they are called Admin, Sales associate and Crew. There is exactly one owner, info@vesperlighting.ca, enforced in the database; the People screen can never assign the owner role. Logins and passwords are created by the owner, and only the owner. The app generates every non-owner password (three common words and four digits, like maple-river-stone-4821), shows it once, and the owner texts it; it is permanent until the owner resets it from People, which also ends that person's open sessions. There is no sign-up, no invite email, no email of any kind, and no self-service password change or reset for non-owners; the sign-in screen says to ask Keenan. The owner changes his own password from Settings.

- `owner`: everything. Home (which is the dashboard), schedule, Meetings (meeting mode's home), pipeline, all leads, all meetings, quotes, and Admin (people, settings, pay).
- `sales`: capture leads and edit their own. Sales users work as a team: every sales user can see every lead, booking and knock session (read only unless it is theirs) so they can cluster meetings and avoid knocking the same doors twice. Contact privacy (Keenan, 2026-11-04): a setter sees a lead's phone number and email only on their own leads (created or assigned to them). On other setters' leads and Keenan's they see the name, address, status and bookings, never the phone or email, anywhere in the app. The database enforces it: nobody reads `leads.phone` or `leads.email` from the table itself, `lead_contacts` returns them only for the leads the person may contact, and `leads.phone_saved` says a number is saved without showing it. View as shows it the same way, and a column added to `leads` later needs its own read grant. They book meetings for their own leads and can move or cancel those bookings until the time starts, see their own activity stats, see their own pay (what they are owed and what they have been paid), and turn their own notifications on or off. Never quotes, never sale prices or revenue, never the owner dashboard, never settings, never anyone else's pay.
- Customers never log in. Anything customer facing is a public link with an unguessable token: the quote link from 2026-11-02 (see Business rules), more in V2.

Enforce this in RLS first, then in the UI. The UI hides what a role cannot see, but the database is the actual gate. Never ship a table without RLS policies. Never bypass RLS with the service role key in a code path a non-owner can trigger.

View as: in Admin > People the owner can open the app exactly as an active non-owner member sees it. A gold bar across the top reads "Viewing as [name]. Read only. Exit." Keenan can click through it (Keenan, 2026-11-03): every screen, sheet, menu and every step of the booking sheet works exactly as it would for them, and nothing is ever saved. The server refuses every write while it is on; steps that need a write to continue (like holding a time) are acted out on screen only, and a final save says "View as: nothing was saved." It is checked on the server on every request: only the owner's own signed-in session can use it, and no session or password of the viewed person is ever used. It shows only what that person's role can see: no pricing, revenue, settings or anyone else's pay. Every new non-owner screen must support View as:
- render from `requireProfile()`, which returns the viewed person while View as is on;
- scope every query to what that role may see instead of relying on RLS alone, because View as reads with the owner's session; a server action that only reads does the same, as the viewed person;
- never write while rendering: a hold, like any write, only ever comes from a tap;
- every write from a tap is refused on the server; the screen acts it out (a held time, a photo, a counter) or says "View as: nothing was saved.", calmly, never as an error;
- be added to the View as comparison test, which checks the screen against what a real test setter sees, and to the click-through test, which proves nothing is written.

## Device rules

Design each screen for the device it will actually be used on, then make it tolerable elsewhere.

- Phone first: lead capture, my leads, tonight's schedule and booking, knock session counters, my pay. Big tap targets, one-handed, works in bright daylight and at dusk. Fast.
- Phone first for customers: the customer quote page, opened from a text message on their own phone.
- iPad first (landscape): meeting mode (presentation plus quote builder), the Meetings page, pipeline board, lead detail with photos.
- The booking sheet is designed and tested at 430 x 932 (Keenan's iPhone 15 Pro Max) and at 390 wide: the extra room goes to bigger type and tap targets, and related items share a screen so there are fewer steps (Keenan, 2026-11-03).
- Desktop and iPad: dashboard, settings, people.
- Navigation: a bottom tab bar on phone and iPad; on screens 1024 px and wider, a slim left side rail with the same items. No top tabs anywhere. Owner tabs: Home, Schedule, Meetings, New lead (the prominent gold button), Leads; Admin (People, Settings and Pay) is a gear in the header, because six items crowd a phone's tab bar (Keenan, 2026-11-02). Sales tabs: Home, Schedule, New lead, Leads, My pay. The owner's Home is the dashboard; there is no separate Dashboard tab. The tab bar lives in the shared app layout so it never reloads, tab links are prefetched, and every tab has a loading screen so a tap responds at once.
- Forms: after an error, a form keeps everything the person typed except passwords.
- Theme: dark by default, with a light theme the user can switch to, remembered per device. Anything printed or exported as a PDF is always white, and so is the customer quote page, which reads like the documents (navy and gold on white, whatever the device's theme). Keep both themes readable. Brand colours: navy `#132E3F`, gold `#B99257`, white, minimal black. Clean and premium, not flashy. No emoji in the UI. No gradients or glassy effects.
- Design skill: the impeccable skill lives in `.claude/skills/impeccable` (Apache 2.0, no hooks), with its product and design context in `PRODUCT.md` and `DESIGN.md`. Every milestone with new or changed screens uses it (Keenan, 2026-11-02): shape before building, critique and polish before the preview, and the before and after scores in the report. These design rules win over anything it suggests: navy and gold, dark by default, no gradients, glassy effects or emoji, calm and premium, phone first for setters. Skip its overdrive, delight and heavy animation.

## Business rules the code must respect

- Pricing defaults live in `settings`, never hardcoded: price per foot (list $24 from 2026-11-04, was $23), control box price ($500), neighbour discount ($150), referral credit ($150), the minimum job ($2,500), how long a quote's prices are held (`price_hold_days`, 120), the service call fee for warranty years 6 to 10 ($200), the rush colour fee (a flat $350 a job, not per foot), the two upper access amounts ($200 with upper runs and no upper gable, $400 with an upper gable), GST rate (5%), GST number, `gst_enabled` (false until the company is registered; while it is off, prices show with no mention of GST at all). On a quote the owner can change every price for that quote only, including custom lines; each quote stores the prices it actually used, so later changes to settings never alter an existing quote. Quotes made before 2026-11-04 keep their own prices and get no rush colour or upper access lines.
- GST display: on screen (meeting mode, quote builder, any price) a total reads like "$3,450 + GST" with no GST dollar figure. Formal documents (the quote PDF the customer signs, later invoices) show subtotal, GST as a dollar amount, total, and the GST number from settings. When `gst_enabled` is off, show the price only and never mention GST.
- Quote total = (total feet x price per foot) + (boxes x box price) + the upper access amount + the rush colour fee + adders - discounts, raised to the minimum job when it comes in under it, then GST if enabled. Upper access follows the runs that are on: none without an upper run, the upper gable amount when an upper gable is on, otherwise the upper amount. Show the breakdown line by line. Round to the cent. Unit tests cover this.
- Setter pay: two kinds of earnings, both with rates in `settings`. Booking pay is a flat amount (default $20) per qualified booking. After each meeting slot the owner marks the booking Qualified, Not qualified (reason from the list in settings), No-show or Cancelled (optional note); only Qualified earns. One booking fee per lead at most; a no-show or cancelled lead can be rebooked and earns when that later meeting is marked Qualified. The fee goes to the setter whose lead it is: the lead's assigned setter, recorded on the meeting when it is booked, whoever picked the time. The owner can correct an outcome until the fee is paid, and the fee is voided or restored to match. Commission is a percentage (default 5%) of the lights and control box after discounts, as actually priced, before GST; the rush colour fee and upper access are left out (Keenan, 2026-11-04, recorded now and built with M5 take 2), and earlier no-shows do not affect it; it is created when the quote is accepted and becomes payable when the lead is marked `installed`, because no customer pays before install. Each earning stores the rate it was calculated at, so a rate change applies to new earnings only. The owner marks earnings paid in batches. Only `sales` users earn: both kinds go to the lead's assigned setter, and leads assigned to the owner earn nothing. The app records pay, it never moves money.
- Dollar amounts live only in `quotes` (sales cannot read them) and `earnings` (sales read only their own). Never copy a price or a total into lead notes, `lead_events.payload` or meeting outcome notes, because sales users can read those.
- No deposits or payments are taken in the app in V1. Quotes state "No payment until your install is complete." Do not build payment capture.
- Meetings: Keenan's evenings start at 5:00 pm with six 35-minute meetings, Monday to Saturday, the drive included (Keenan, 2026-11-04; the first defaults were 6:00, 6:45, 7:30 and 8:15 pm, 45 minutes each). Configurable in settings; whatever Settings says is Keenan's choice, so never flag it. From Schedule, Keenan can give one evening its own start, meeting length and number of meetings ("Just this day"), or change them for all days (which updates Settings). Open times, holds and booking read the evening's own schedule when it has one, otherwise the defaults. A day change never moves or cancels a booking: one that no longer lines up stays at its time, and no time that overlaps it can be booked. Each meeting records its host in its own column (Keenan for now), not tied to the owner role. Bookings open 14 days ahead. Setters can hold, book or move into a time until 30 minutes before it starts (in settings); the owner until it starts. Setters can move or cancel their own upcoming bookings until the time starts, and the owner any booking; cancelling sends the lead to Follow up for the next day. After the time starts, outcomes are owner only. Warn (do not block) when the booked address is more than 10 km in a straight line from the meeting before or after it.
- No double booking is a hard rule (Keenan, 2026-11-01). Two people can never take the same time, and a time is claimed the moment someone starts booking it:
  - tapping an open time places a hold; everyone else sees the holder's initials on it within a few seconds and cannot pick it;
  - a hold lasts 5 minutes (in settings), shown as a countdown, and only the holder can add 5 minutes to it; the timer is what frees a time, and the hold also ends at once when the holder books, lets go, picks another time or leaves the sheet (Keenan, 2026-11-03, replacing the check-in grace period);
  - one hold per person; booking takes the caller's own hold or a free time, never a time someone else holds;
  - all of it is enforced in the database, under the same lock as booking.

  Any change touching slots, holds or bookings must keep these tests passing: the database race tests (two people grabbing or booking the same time at the same instant, repeated many times per run, on the default times and on an evening with its own schedule; grabbing or booking a held time; a hold running out; only the holder can extend, and never once someone else has the time; one hold per person), the slot checks, and the live walk-through with two setters racing for the same time through the booking sheet.
- The booking sheet is the only way to book (Keenan, 2026-11-02; round 2, 2026-11-03). Tapping an open time holds it and opens a full-screen sheet over the schedule:
  - the header has the Vesper wordmark on the left and the held time on the right with its countdown; tapping the time opens a small menu at once (Add 5 minutes, Change time, Let go), no double-tap or press-and-hold; with under a minute left it says so and offers Add 5 minutes; if it runs out, the sheet says so and offers to hold it again while it's still free;
  - the steps follow the visit, each clearly labelled: At the door holds only what is needed face to face to book (name, phone, owns the home, wants a price, everyone who decides will be there); After the door, on the sidewalk, holds the rest of what they learned (Christmas lights now, looked into it before, which areas, timing), then the address, the soffit colour and the photos; then Book;
  - a progress bar with a clear counter beside it ("Step 3 of 6, 3 left"), a "?" with that step's note, and a bottom bar that is always there with Back and Next (primary, bottom right, in thumb reach); swiping left and right moves between steps too;
  - related items share a screen so there are fewer steps; one-tap answers, no scrolling on a phone where it can be avoided, and nothing important at the top centre;
  - leaving the sheet keeps what was entered as a draft on that phone, wiped after 24 hours; setters see an Unfinished list on Home, and tapping one reopens it where they left off and asks them to pick a time.
  New lead's "Save and book", the lead page's "Book a meeting" and Move open the same sheet, prefilled.
- Saving a new lead never makes a copy (Keenan, 2026-11-04). The phone makes a save key once per new lead, the first time the booking sheet or New lead saves that person, keeps it in that phone's draft, and sends it with every try. A unique index on `leads.save_key` lets only one lead have it, so a try after a lost answer gets back the lead the first try made, brought up to date with what's on screen, never a second copy. Only the person who made the lead gets it back.
- Before you book (M3): a lead can be booked only when all of these hold:
  - a phone number is saved;
  - Owns the home is Yes;
  - Wants a price is Yes;
  - Soffit colour is answered (Not sure is fine);
  - the Front, Left corner and Right corner photos exist, or the setter picks a skip reason (Homeowner said no, or Other with a note), which the owner sees on Schedule;
  - everyone who decides on the house will be at the meeting: asked at the door as a question, stored on the lead and on the booking;
  - the lead has a map position: an address picked from the suggestions, or, for a brand-new street Google doesn't have yet, the phone's GPS position taken at the door ("Use where I'm standing"), accurate to 50 m or better (Keenan, 2026-11-01).

  The owner's own leads follow the same rules. Not collected is never an answer here: Not collected for the phone, owns the home, wants a price or everyone who decides blocks booking, with a clear note on what's missing (Keenan, 2026-11-03). Wherever an answer rules booking out, the note offers Keep as a lead, which lets the time go at once and keeps the person as a lead (round 2 polish, 2026-11-03).
- The door process: a setter's visit is a short conversation with a structure: open, find out, photos, book. The app follows it with the booking sheet's steps, a short note per step that Keenan edits in Settings (they replaced the single Door guide), the Find out questions and four guided photos.
  - The questions (Keenan, 2026-11-03): phone, owns the home, wants a price, everyone who decides will be there, Christmas lights now, looked into it before, which areas and timing each take an answer or "Not collected". A step can't be finished, and a lead (New lead included) can't be saved, until every one of them on it has an answer, Not collected included; a small "Mark the rest Not collected" button does it in one tap. They can be answered in any order. The soffit colour keeps its "Not sure" answer and is needed to book, not to save.
  - Each lead shows how complete it is, as "6 of 8 collected" (those eight questions): on Keenan's Tonight, Schedule, the Meetings page and the lead page, and on the setter's own bookings. Information only; it never affects pay.
  - Each guided photo slot has a big Take photo button, a smaller Upload button for a photo already on the phone, and a simple line drawing showing the angle to shoot.
- Lead statuses: `new`, `follow_up`, `meeting_booked`, `met`, `quoted`, `sold`, `installed`, `lost`. Every status change writes a `lead_events` row with who and when. `lost` requires a reason. `follow_up` requires a follow-up date, the day to come back, and leaving `follow_up` clears it; both are enforced in the database. Setters change status only between `new`, `follow_up` and `lost`; booking a meeting sets `meeting_booked`, and the owner sets everything after it. In V1 the owner sets `installed` by hand after the crew is done; jobs arrive in V2.
- Track colour: white is the only stock track colour.
  - Keenan manages the Track colours list in Settings: a name and an optional RAL code each. Colours can be added, renamed, reordered and retired, never deleted, so old leads keep theirs. It starts with White, Off-white, Brown, Black and Grey.
  - Only the owner sets a lead's track colour, enforced in the database: one of the active colours, or Custom with a RAL Classic code (the system in Keenan's RAL K7 colour book), checked against the RAL Classic list and shown by name.
  - No on-screen colour swatches anywhere, since screen colours aren't accurate.
  - Setters can see the track colour but not set it. Their soffit question at the door stays as it is.
  - A quote can't be marked ready until the track colour is set (M5). The quote stores the colour name and RAL code it used, and a Custom colour shows as needing powder coating.
- Meeting mode (M5) is customer-facing the whole time: full screen on the iPad, no tabs, and nothing internal ever on screen: no costs, margins, setter names, pipeline or other customers. Owner only, enforced on the server. The track colour is confirmed and initialled by the customer at every meeting, stored on the lead with a timeline event. Presentation content and images come from Settings, never from code; a page with no content is skipped, never shown empty; only Vesper's own photos appear in anything a customer sees. Opened once with signal, meeting mode keeps working without it: content and images cached on the iPad, quote math on the iPad, the draft on the iPad until saved; saving needs signal and says so. Track colour pricing: stocked included; non-stock included on the factory order (spring); this season adds the flat rush colour fee from Settings (2026-11-04, replacing the per-foot fee). A fee that is not set (rush colour, service call) hides its line instead of showing a blank. Each run has a part of the house (eave, gable, garage, porch, sides, other) beside its level; the quote builder guesses it from the run's name and Keenan can change it. Every quote holds its prices until a date, default `settings.price_hold_days` (120) days out.
- Customer quote link (Keenan, 2026-11-02; take 1 now, take 2 with M5 take 2). After a meeting Keenan sends the homeowner a private link to their quote: a public page with no login, opened by an unguessable token, reading the same lead, runs, prices and mockup as meeting mode. One source of truth:
  - the token has at least 128 bits of randomness and lives only in the owner-only `quote_links` table; one live link per lead; revoking kills it, and sending again issues a new one; updating the quote updates what the same link shows;
  - the public page reads through one database function that takes the token and returns only customer-safe fields; anonymous callers have no access to any app table; the mockup loads through a short-lived signed URL that only a request carrying a live token can sign; their selection, Book my install and a visit are written through token-scoped functions that change nothing else;
  - the customer never sees costs, setter names, notes, the timeline, statuses or other customers;
  - totals come from `lib/pricing.ts` on the page and on the server; the server recomputes every total from the stored quote and the selected runs, never from a total the browser sends; the control box is always included; an extra-work line marked "only with upper runs" drops off when no upper run is selected; when a selection falls below the minimum job total in Settings (empty by default), the total rises to the minimum with a line saying so; GST display as above;
  - visits are counted with no IP address or device fingerprint stored, and a signed-in member's own visits don't count;
  - Book my install saves the chosen option and notifies Keenan; it never accepts the quote or creates commission; Keenan still marks the quote accepted after signing;
  - the push goes to the person who made the link (Keenan) through standard web push from the installed app, keys in environment variables. The secret Supabase key never runs in a customer's request: the database hands the server the addresses sealed, and only the server can open them;
  - quote pages are noindex, no-referrer and not cached, answer on any host, and links are built from `QUOTE_BASE_URL`; on quote.vesperlighting.ca only quote routes answer;
  - prices are held, links don't expire (Keenan, 2026-11-04): a link stays live until Keenan revokes it; under the total a quiet "Price held until [date]", and after that date the page still works and says "Prices may have changed since [date]. We'll confirm before booking.", and Book my install still works; a revoked link shows a closed page with call and text buttons and no prices;
  - the page is a sales tool, phone first (the rework, Keenan, 2026-11-04): their house and price first, a Christmas banner (Settings, September 1 to November 30), six product points from Settings, their runs with a house diagram that lights the parts in their quote, Start smaller, track colour, Warranty, install day and Vesper's install photos behind taps, and a bottom bar with Book my install, call and text; under the $2,500 minimum it says "That's under our $2,500 minimum, so this option comes to $2,500." and "Need a repair or something smaller? Call or text us and we'll see what we can do." See the spec for the page.
- Setters' first sign-in and notifications (Keenan, 2026-11-03):
  - the first time a setter signs in, a short welcome: add Vesper to the home screen, allow location, turn on notifications, each skippable; then a one-screen tour of the door flow. Never shown again once done; Keenan can reset it from People;
  - a setter gets a push when Keenan marks one of their bookings (Qualified, Not qualified, No-show, Cancelled) or moves or cancels it. Notices show on a lock screen, so they name the street only (never a house number), and never a customer's name, a phone number or another setter's details; a reason comes from the fixed list, never from a note typed by hand;
  - setters turn their notifications on or off themselves, from Notifications (the bell in the header).
- Every customer facing string (quote PDF, presentation, quote page) is written in plain language with no em dashes, no buzzwords, and no promises the business cannot keep. Use the exact warranty wording from `settings.warranty_text`.

## How to work in this repo

1. Start every session by reading this file, the current milestone in `docs/03-roadmap.md`, and the relevant parts of the spec and data model.
2. Plan before building. Post a short plan (files, schema changes, risks) and wait for approval on anything that touches the schema, RLS, auth, or pricing.
3. Small, complete slices. A milestone is done when every acceptance criterion in the roadmap passes, the app builds with no TypeScript errors, `npm run lint` and `npm test` pass, and the flow works on a phone-sized viewport.
4. Every database change goes in a migration file in `supabase/migrations/`, with a short comment on what and why:
    - this covers tables, policies, functions, triggers, views, grants, seed rows and storage buckets alike;
    - never make a database change by hand in the Supabase dashboard or with ad hoc SQL;
    - never edit a migration that has already been applied; add a new one;
    - prefer additive changes: add columns, enum values and tables rather than replacing or removing them. An unused enum value is fine;
    - never put destructive SQL text (drop, delete, truncate) in a Supabase connector call, not even quoted inside a read-only query: the connector waits for a human to confirm and times out. If a migration truly has to drop or delete something, stop before applying it and tell Keenan, so he can be at the screen to approve it;
    - name each file `<version>_<name>.sql` with the version the database recorded for it. The Supabase connector picks the version when it applies a file, so rename the file to match `supabase_migrations.schema_migrations`. A fresh, empty Supabase project then reaches the same schema by running the files in order;
    - regenerate types after schema changes.

    Settings that can only live in the dashboard are listed in `docs/05-supabase-setup.md`; update that list whenever one of them changes.
5. Commit in small logical commits with plain messages. One branch per milestone, merged when done.
6. Never commit secrets. All keys go in `.env.local` and Vercel environment variables. `.env.example` lists every variable with a comment. Nothing in the app, the tests or the scripts hard-codes a Supabase project's URL, ref or keys; they come from environment variables, so pointing anything at another project is a configuration change. Never put a secret key in a `NEXT_PUBLIC_` variable (Keenan, 2026-11-02):
    - anything in a `NEXT_PUBLIC_` variable is copied into the JavaScript every visitor downloads;
    - the publishable key (`sb_publishable_...`, or the legacy anon key) is the only Supabase key that goes in one;
    - the secret key (`sb_secret_...`, or the legacy service_role key) goes only in `SUPABASE_SERVICE_ROLE_KEY`;
    - the build refuses to run if any `NEXT_PUBLIC_` value is a Supabase secret key (`lib/public-env-guard.ts`, run from `next.config.ts`). Keep that check, and never work around it.
7. When something in the docs is unclear or wrong, stop and ask instead of guessing. When you make a judgment call, write it down in `docs/decisions.md` with the date.
8. Keep the dashboard honest: every number shows what it counts and the date range. No invented or placeholder numbers in production views. Empty states say what will appear and how to make it appear.
9. Do not add features that are not in the current milestone. Put ideas in `docs/backlog.md`.
10. Test on the real thing: the live walk-through drives the app in a phone-sized browser against the real database. No second Supabase project for now, and don't recommend one (Keenan): tests create test-prefixed accounts and data on production and clean up after themselves. The app stays ready to add a second project whenever Keenan asks: migrations only (rule 4), no hard-coded project details (rule 6), and the setup steps in `docs/05-supabase-setup.md`. The View as test signs in as the owner through a one-time server-side session (approved by Keenan on 2026-10-28). It follows these rules:
    - no password is used or changed, and no email is sent;
    - it only views; it never creates, changes or deletes anything, members included, since only the owner adds members;
    - forms it submits are refused before anything saves;
    - it ends that session afterwards.

    Anything the walk-through cannot reach is named in the report.
11. After building, run the full automated suite: unit, RLS, smoke, build, and the live walk-through with test-prefixed accounts, deleted after, plus the owner's one-time session for View as. Keenan does not run checklists; he looks at a preview only for what customers see (rule 13).
12. If anything fails, do not merge. Stop and report what failed.
13. If everything is green, how it ships depends on whether customers see it (Keenan, 2026-11-04, replacing the 2026-11-02 rule):
    - anything customers never see (setter and owner screens, fixes, tests) merges on green, straight to live: merge the branch into main, verify production after the deploy, and put the production link first in the report;
    - anything customers see (the quote link, meeting mode, which the customer watches the whole time, its presentation included, the quote PDF and other documents) waits for a preview: push the branch and put a clickable Vercel preview link first in the report, which Keenan opens on his iPad (Vercel may ask him to sign in to Vercel first). Only when he says "push the changes" is the branch merged into main, with production verified after the deploy and the production link reported;
    - a branch that changes both waits for the preview.

    Either way the report gives a short list of what changed, where to see it, and anything he needs to upload or set first. No test checklists for Keenan, ever.

## Definition of done for V1

An appointment setter can install the app on their phone, log in, capture a lead at a door in under 30 seconds with a photo and a geocoded address, book that lead into one of tonight's open slots without double booking, and see what they are owed. The owner can see tonight's meetings on his phone, mark bookings qualified, run a meeting on his iPad with the presentation and a quote that prints to a clean PDF, move leads through the pipeline, mark setters paid, and see a dashboard that answers: how many doors, conversations, meetings, quotes and sales this week, by person, what each setter is owed, and which sold jobs are waiting to be installed.
